REPO CANVAS 0.5.0 — УСТАНОВКА АГЕНТОМ В СУЩЕСТВУЮЩИЙ ПРОЕКТ

Ты устанавливаешь локальную визуальную карту проекта. Пользователь не обязан объяснять устройство Repo Canvas и вручную описывать архитектуру. Выполни весь сценарий самостоятельно, не меняя продуктовый код во время первичного построения карты.

В корне проекта рядом с этим текстом должен лежать файл `repo-canvas-0.5.0.tgz`.

1. Прочитай существующие корневые инструкции проекта и проверь `git status`. Сохрани все пользовательские и чужие изменения.

2. Проверь Node.js 22+ и npm. Если их нет, не устанавливай системные компоненты сам: сообщи владельцу, чего не хватает.

3. Из корня проекта выполни:

   npm install --save-dev --save-exact --ignore-scripts ./repo-canvas-0.5.0.tgz
   npx --no-install repo-canvas init

   Если package.json отсутствовал, npm создаст минимальный служебный manifest. Не запускай `npm init` и не выдумывай метаданные продукта. Инициализатор должен сохранить существующие AGENTS.md, CLAUDE.md, .gitignore, scripts и пользовательский код. При конфликте остановись, ничего не перетирая.

4. После init заново полностью прочитай `AGENTS.md` и `repo-canvas/SKILL.md`. Дальше канонические правила находятся там.

5. Запусти ровно один сервер в устойчивом терминале:

   npm run repo-canvas:start

   Используй существующий здоровый сервер этого проекта, если он уже запущен. Не убивай посторонние процессы. Если 4173 занят чужим процессом, выбери явный свободный порт через `npm run repo-canvas -- start --port <port>` и сообщи ссылку.

6. Проведи read-only bootstrap. Изучи инструкции, основные документы, manifests, entry points, крупные runtime/data boundaries, верхнеуровневую структуру и текущий git status. Построй человеческую смысловую карту, а не зеркало папок:

   - все смысловые области, необходимые для понимания реального проекта;
   - все постоянные работающие сущности независимо от их количества: четыре для маленького проекта или сотни для большого;
   - все важные связи данных, управления и runtime без искусственного лимита;
   - короткие паспорта: назначение, вход, результат, зависимости, основной путь.

   Область — большая рамка вроде «Обработка документов» или «База знаний».
   Сущность — функционирующий модуль/ответственность вроде «Нормализатор» или «Поиск стандартов».
   Текущая задача — маленький спутник возле затронутых сущностей, а не отдельная большая зона.

7. Публикуй карту постепенно через `npm run repo-canvas -- ...`: сначала area, затем entity, затем relation. Не создавай сущность на каждый файл или класс.

8. Если назначение важного компонента или его место на карте действительно неоднозначно, не выдумывай. Задай владельцу короткий конкретный вопрос. Не блокируй независимую часть bootstrap без необходимости.

9. Отобрази только подтверждённую текущую работу. Создай по одной маленькой `work`-ноде на каждую реальную задачу/сессию и прикрепи её ко всем затронутым entity через `--targets`. Активная работа должна иметь locator текущей сессии. Не считай весь грязный worktree активной работой.

10. Статусы сущностей используй буквально:

   operational — существует и должна работать;
   disabled — намеренно отключена или заморожена;
   problem — только подтверждённая воспроизводимая проблема, падающий тест, инцидент или явно записанный дефект;
   planned — одобренная, но ещё не реализованная сущность.

   Наличие работы вычисляется по work-сателлитам. Не назначай модулю отдельный статус active.

11. Выполни `npm run repo-canvas -- check`, затем открой Canvas в браузере и проверь глазами: области читаются, сущности находятся внутри правильных областей, связи не превращают экран в лапшу, задачи выглядят маленькими спутниками, активные сущности заметно анимированы, горизонтального скролла страницы нет.

12. Верни владельцу кликабельную локальную ссылку, перечисли построенные области, активные задачи и сессии, конкретные вопросы по неоднозначным местам и результат `repo-canvas check`.

После установки при каждой следующей задаче соблюдай AGENTS.md: после короткого read-only анализа, но строго до первой правки продукта, отдельной короткой командой запускай `npm run repo-canvas -- work start ...` и жди `verified: true`. Не объединяй регистрацию с тестами, установками и другой работой. Затем обновляй только затронутые паспорта и закрывай work после проверки результата.

После `init` сообщи владельцу: Codex может один раз попросить доверие к `.codex/hooks.json`; его нужно подтвердить. Жёсткий барьер действует в новых сессиях, открытых после установки. Текущая установочная сессия следует тому же порядку через AGENTS.md.
